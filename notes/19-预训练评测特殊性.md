# Day 19｜预训练评测的特殊性

> 整理于 2026-10-09。本文是基于已有实验和公开资料的学习笔记；没有运行新的预训练 checkpoint，也没有把 DeepSeek API 小实验写成完整 MMLU 成绩。Day 19 已用 OpenCompass 跑通 Qwen2.5-1.5B 的 C-Eval 19 题验证，证据见[实跑报告](../reports/19-opencompass-qwen15-ceval19.md)。

## 先用一句话理解

**预训练评测**要回答：“模型随着训练不断读入数据，基础能力是否在增长、哪些能力出现停滞或退化、下一个 checkpoint 值不值得继续训练？”因此它看的是**一条随训练进度变化的曲线**，不只看最终模型的一次总分。

一个简化的过程是：

```text
checkpoint A → 固定验证集 loss / PPL + 小型能力题集
checkpoint B → 同样的验证集、题集和评测口径
checkpoint C → 同样的验证集、题集和评测口径
                          ↓
             比较趋势、异常跳变、能力退化，再决定是否深入评测
```

公开的 [Pythia 项目](https://github.com/EleutherAI/pythia)提供训练过程中多个 checkpoint，并保存跨训练阶段的 benchmark 结果，是研究这种“能力随训练变化”的具体例子。

## 为什么要评 base model？

**Base model** 是以续写、预测下一个 token 为主要训练目标的模型。它能体现预训练阶段获得的语言建模、知识和部分推理能力，但未必稳定遵循“请只输出 A/B/C/D”这样的指令。**Instruct/chat model** 在基础模型之上又经过指令微调等后训练，因此最终回答也受到后训练的影响。

如果问题是“本次预训练有没有让基础能力变强”，应优先比较同一训练流程中的 base checkpoint；只测 instruct 模型，无法把变化可靠地归因于预训练。但这不表示 instruct 模型不用评：产品使用中的指令遵循、帮助性、格式与安全表现，仍要在后训练阶段单独评。

同一选择题在 base 与 chat 模型上可能需要不同的提示词与评分方式。Base 模型常用续写式 few-shot，或比较候选答案的条件似然；chat 模型可用对话模板要求生成答案。**方法必须和模型形态匹配，并在跨 checkpoint 对照时保持一致。**[OpenCompass 的说明](https://opencompass.readthedocs.io/en/latest/get_started/faq.html)把多选题的候选似然方式称为 `ppl`，生成回答称为 `gen`；这里的 `ppl` 是框架中的选项比较模式，不应与下文“验证语料 perplexity”混为一谈。


## 验证语料预测指标与 benchmark 分数

| 指标 | 问的问题 | 能看到什么 | 单独使用的局限 |
| --- | --- | --- | --- |
| 固定验证语料的平均 token loss / Perplexity（PPL） | 模型平均给真实下一个 token 多大概率？PPL 是 `exp(平均 loss)` 的换算值 | 同一预测结果的两种刻度；越低越好 | 受验证文本、分词器、上下文切分等影响；不能推出每个具体任务都涨分 |
| Benchmark 准确率/精确匹配 | 在特定任务与判分规则下答对多少题？ | 知识、推理、格式等任务能力的直接证据 | 受题量、提示词、shot、抽取和样本构成影响；小样本波动大 |

对自回归语言模型，若 `loss` 是每个 token 的平均负对数似然，则 **PPL = exp(loss)**。例如平均 loss 为 0.693 时，PPL 约为 2；同一语料、分词器和计算方式下，二者严格同步变化，**同时报告它们不会增加一份独立证据**。之所以都能见到，是因为训练和排障常看原始 loss，而有些报告用 PPL 表达相同的预测难度。两者与 benchmark 答题分数才是真正不同的问题：[Hugging Face 的语言模型文档](https://huggingface.co/docs/transformers/en/tasks/language_modeling)展示了从评估 loss 计算 PPL，[PPL 说明](https://huggingface.co/docs/transformers/v4.38.0/perplexity)指出上下文长度和切分方式会影响计算。因此，“loss 从 2.0 降到 1.9”说明模型对所选验证文本的预测改善，**不能推出 MMLU 必然上升多少个百分点**。

这里要区分两种“长度影响”：**仅把相同难度的 token 增加到语料中，不会因为整段联合概率变小而机械地降低 PPL**，因为最后按参与评分的 token 数取平均；但文本长到超过模型上下文窗口后，切块或滑窗步长会改变某些 token 能看到的前文，从而改变它们的条件概率、平均 loss 和 PPL。比较结果时必须固定窗口、步长、边界处理以及计入评分的 token。Hugging Face 的上述示例在同一 WikiText-2 语料和模型上，改变滑窗步长后报告了不同的 PPL，说明的是**输入上下文和评测算法改变**，不是“句子越长 PPL 必然越小”。

## 为什么要比较不同 checkpoint？

只看最后一个模型，会错过训练过程的信息。例如验证 loss 持续下降而某项 benchmark 停滞，可能需要检查该能力是否对这批验证文本不敏感、题目量是否太小、评测输入是否改变；若某次分数突然下降，也要先排查数据与评测设置，再判断是否真的退化。

比较 checkpoint 时至少固定：验证/测试集版本与题号、提示词、few-shot 示例和顺序、tokenizer、精度、推理配置、答案抽取、指标、框架版本；记录 checkpoint 的训练 step 或已见 token 数。若这些东西变了，曲线中的变化可能来自评测口径。对于同一架构的连续 checkpoint，固定 tokenizer 尤其重要。

本项目此前的[方差报告](../reports/17-variance.md)表明：即使模型权重不变，只改 few-shot seed，分数也可能变化。预训练曲线上的小幅起伏不能直接解释为能力真实增长或退化。

## 频率与成本：怎样安排评测？

这是一个**工程设计建议，不是所有团队统一执行的规则**：

1. 每个希望监控的 checkpoint 跑固定验证集 loss，并跑一个规模可控、能及时反馈关键能力的题集。
2. 定期跑覆盖面更广的基准任务；发现异常跳变或到达关键训练阶段时增加针对性评测。
3. 昂贵的长生成、代码执行、人工或模型裁判评测，按里程碑或异常触发运行，并记录额外成本。
4. 先估算“checkpoint 数 × 题数 × 每题候选数/生成 token 数 × 模型推理成本”，再确定频率。多选题的候选似然往往减少答案抽取问题，但每题可能要评分多个候选，**不能笼统断言它一定比短生成省算力**。

训练中的高频监控需要稳定且便宜的指标，最终模型则需要更全面的能力、风险和用户场景评测。两者服务的决策不同。

## 预训练与后训练评测的区别

| 维度 | 预训练阶段 | SFT / 偏好优化等后训练阶段 |
| --- | --- | --- |
| 核心问题 | 基础预测能力与任务能力是否随训练进展？ | 是否遵循指令、给出有用且合适的回答？ |
| 评测对象 | 多个 base checkpoint | instruct/chat 模型及其版本 |
| 典型指标 | 固定验证 loss/PPL、知识与推理题集趋势 | 指令遵循、任务成功率、答案质量、安全与格式等 |
| 常见输入 | 续写式、few-shot、候选似然；须固定模板 | 对话模板、系统指令、开放式任务 |
| 决策节奏 | 随 checkpoint 重复，追踪趋势和异常 | 比较后训练方案、发布前验收与上线后监控 |

这是侧重点，不是互斥清单：预训练也可以测生成，后训练也可以测知识题；关键在于明确当前要支持什么决策。

## 为什么 DeepSeek 的 42/50 不能直接对比完整 MMLU 榜单？

本项目[Day 18 报告](../reports/18-deepseek-mmlu50.md)记录的是：从 `cais/mmlu` 的 **14,042** 道 `test` 题里随机取 **50** 题，覆盖 26 个学科，用 DeepSeek Flash 做 **0-shot、生成单个大写字母、严格匹配**，得到 **42/50 = 84.0%**。MMLU 原始设计涉及 [57 个学科](https://arxiv.org/abs/2009.03300)。

1. **题目不是同一批。**50 题仅占完整 test 的约 0.36%，覆盖的学科、每科题数和难度构成与全量不同；一题就影响 2 个百分点。报告给出的 Wilson 近似区间为 71.5%～91.7%，提醒我们小样本估计不精确。
2. **评测方式可能不同。**榜单可能用不同的 shot、示例、提示词、chat template、生成或选项似然、答案抽取与聚合。即使题目相同，换这些设置也可能换分数。[OpenCompass 数据集配置说明](https://opencompass.readthedocs.io/en/doc_refactor/user_guides/datasets.html)明确要求核对数据、prompt、few-shot 和 evaluator。
3. **模型对象可能不同。**本实验请求的是服务端名称 `deepseek-flash`，保存了响应中的模型名和指纹，但未锁定可下载的权重 revision；榜单可能是另一个服务版本、base/instruct 版本或根本不是同一模型。

所以，84.0%可以准确表述为**“本次 DeepSeek Flash 在固定抽样和指定 0-shot 规则下答对 42/50”**。若要与某个榜单做有效对照，先确认模型版本、测试题集合和评测协议相同；做不到时，只能把公开分数作为背景，逐项说明口径差异，不能据此得出“超过/落后榜单多少分”的能力结论。

## Day 19 选 OpenCompass 后怎么衔接？

OpenCompass 官方把一次评测拆成**配置 → 推理 → 评分 → 汇总**；数据配置含加载、输入构造和判分规则，[快速入门](https://opencompass.readthedocs.io/en/stable/get_started/quick_start.html)提供最小实例。本项目已在同一模型与同一批 C-Eval 题上完成[OpenCompass 实跑](../reports/19-opencompass-qwen15-ceval19.md)，但两框架的 prompt 与评分方式尚未完全对齐。仅在两个框架里各跑出一个总分，不足以说明实现一致；严格对拍仍须固定**同一模型、同一批题、同一 prompt、同一评分规则**，再比较逐题输入与结果。

Day 19 的另两份交付见[四框架横评](../reports/19-框架横评.md)和[Qwen 公开成绩对照](../reports/19-对齐公开结果.md)：前者区分本机实跑与文档调研，后者逐项写明 shot、样本范围和评分口径的差异。

**面试用一句话：**“预训练评测关注多个 base checkpoint 的能力曲线：用固定验证 loss/PPL 看语言建模进展，用固定任务集看具体能力；高频监控和全面评测分层安排，并锁定数据、prompt 与判分口径，避免把评测噪声误判为能力变化。”
