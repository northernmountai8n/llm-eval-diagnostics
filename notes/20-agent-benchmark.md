# Day 20｜Agent 评测与传统题库评测

## 先看评测单位

MMLU / GSM8K 给模型一道题，再根据选项或最终数字打分。Agent 任务通常允许模型连续观察、调用工具、修改环境，再根据最终产物或环境状态判定是否完成。区别在**任务流程和可观察结果**；不能笼统说“Agent 评测都按操作轨迹打分”。轨迹通常用于诊断，官方成功条件因基准而异。

| 基准 | 要完成的事 | 主要成功判定 | 容易漏看的诊断信息 |
| --- | --- | --- | --- |
| MMLU / GSM8K | 回答选择题 / 算术题 | `acc` / 最终答案 `exact_match` | 题目、提示词、抽取规则 |
| [SWE-bench](https://www.swebench.com/SWE-bench/faq/) | 根据真实 GitHub issue 给仓库打补丁 | 在规定仓库环境中应用补丁并运行测试，统计 resolved | 搜索与编辑过程、补丁是否可应用、环境或测试失败 |
| [GAIA](https://arxiv.org/abs/2311.12983) | 解需要推理、浏览、工具使用，有时含附件/多模态的现实问题 | 最终答案的正确性；过程可用于定位问题 | 检索依据、工具调用、附件读取、来源变化 |
| [τ-bench](https://arxiv.org/abs/2406.12045) | 与模拟用户对话，按领域政策调用 API 完成事务 | 比较最终数据库状态与目标状态；还报告多次运行可靠性 `pass^k` | 是否遵循政策、工具调用顺序、状态更改、用户模拟波动 |
| [Terminal-Bench](https://www.tbench.ai/news/announcement) | 在隔离终端环境里完成软件/系统任务 | 专门环境中的测试检查任务结果 | 命令轨迹、文件改动、运行日志、测试输出 |

## 一次 Agent 评测的数据流

```text
任务说明 + 初始环境 + 可用工具 + 限额
    → Agent 多轮观察 / 思考 / 调工具 / 改环境
    → 最终答案、补丁或环境状态
    → 对应基准的答案匹配、测试或状态检查
    → 成功率；保留轨迹以复核失败原因
```

例如 SWE-bench 的评测器会建仓库的 Docker 环境、应用提交的补丁并运行测试；它的成功条件是问题是否被解决，不是每一步命令是否“好看”。GAIA 即便需要工具和多步检索，最终评分仍围绕答案；τ-bench 强调目标数据库状态，`pass^k` 用来观察多次尝试是否稳定成功。[来源：SWE-bench FAQ](https://www.swebench.com/SWE-bench/faq/)、[GAIA 论文](https://arxiv.org/abs/2311.12983)、[τ-bench 论文](https://arxiv.org/abs/2406.12045)。

## 做实验时要记录什么

1. **固定任务和环境**：题目版本、仓库提交、容器镜像、工具版本、可访问资源、用户模拟器与模型版本。在线资料若可能变化，保留检索时间和证据。
2. **固定运行协议**：提示词、最大步数、时间/费用/令牌限制、采样参数、重试规则。并发或 API 故障要单独统计，不应混成模型能力失败。
3. **同时留结果与过程**：最终回答/补丁/数据库状态、测试结果，以及工具请求、返回、错误和时间。失败时才能定位是规划、工具使用、环境还是判分问题。
4. **分清重复运行指标**：单次成功率与多次运行稳定性含义不同。`pass^k` 指同一任务连续 `k` 次都成功的可靠性度量；它不等于“`k` 次中至少成功一次”。
