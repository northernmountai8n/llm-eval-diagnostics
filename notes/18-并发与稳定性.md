# Day 18｜异步并发、重试与断点续跑

> 2026-10-08 的实操。客户端是 [`src/async_eval.py`](../src/async_eval.py)，服务端是 [`src/day18_mock_api.py`](../src/day18_mock_api.py)。**服务端只模拟等待和故障，没有加载语言模型。**下列吞吐数字不能当作 Qwen 的推理性能，也没有评测准确率。

## 一句话理解

一次评测要向模型 API 发很多题。等待第 1 题回复时，可以先发第 2、3 题；每题完成就保存结果。临时错误可重试，持续失败要单独记录；重新启动时，只请求成功文件里还没有 ID 的题。

```text
待跑题目 → 限制并发数 → 请求 API → 临时错误时重试
                               ├─ 成功：追加一行 JSONL，记录 ID 和回复
                               └─ 失败：追加失败日志，不中断其他题
重启 → 读取成功文件中的 ID → 跳过这些题 → 继续其余题
```

## 脚本实现了什么

| 机制 | 代码中的做法 | 用处 |
| --- | --- | --- |
| 异步并发 | `asyncio.as_completed` 收集已结束的请求，`httpx.AsyncClient` 复用客户端 | 等待一题时处理其他题；先完成的结果先保存 |
| 并发上限 | `asyncio.Semaphore(concurrency)` 只包住网络请求 | 不让所有请求同时压向服务端；退避等待不占并发名额 |
| 超时与重试 | 默认每次请求超时 5 秒；最多重试 2 次，退避 0.25、0.50 秒 | 处理超时、连接故障、HTTP 429 和 5xx；普通 4xx 不盲目重试 |
| 增量落盘 | 成功一题就向 JSONL 追加一行，并 `flush`、`fsync` | 中途退出时保留已完成题目 |
| 断点续跑 | 启动时读取成功 JSONL 的 `id`，只请求缺少的 ID | 避免重复消耗时间和 API 配额 |
| 失败隔离 | 单题重试仍失败时写入单独的 `.failed.jsonl`；其他题继续 | 失败题可稍后补跑；批次退出码为 1，提醒仍有未完成题 |
| 进度与日志 | 每题完成或失败时记录事件和 ID，结束时报告成功数、失败数、耗时、吞吐 | 能定位失败题和分析运行效率 |

成功文件是**当前完成状态**；失败文件是**历史失败事件**。失败题后来成功，失败文件仍保留原记录。判断是否还有欠题，应对照预期题目 ID 和成功文件，不能只看失败日志行数。

客户端也接受 `--input` 指向 UTF-8 JSONL 题目文件。每行需有整数 `id` 和非空 `question`，可选 `gold`。指定 `gold` 时保存逐题 `exact_match`，全部带答案的题都成功后输出汇总；这是对原始回复做 `strip()` 后的**严格字符串比较**，正式 benchmark 还需按任务规定做答案抽取和判分。`--model`、`--url` 可指定 OpenAI chat-completions 兼容服务；需要认证时用 `--api-key-env` 指定保存密钥的环境变量名，命令行不直接写密钥。续跑时脚本核对相同 ID 的题干、参考答案、模型名和 URL，防止把明显不同配置写入同一结果文件。

## 实测过程

在项目目录激活 `lmeval` 环境后，先在一个 PowerShell 窗口运行 `python .\src\day18_mock_api.py`，保持服务运行；另一个窗口运行下列三条命令。三次均不传 `--out`，因此不会因续跑跳过题目：

```powershell
python .\src\async_eval.py --count 16 --concurrency 1 --timeout 10
python .\src\async_eval.py --count 16 --concurrency 4 --timeout 10
python .\src\async_eval.py --count 16 --concurrency 16 --timeout 10
```

### 并发与服务端瓶颈

模拟服务每个成功请求等待 1 秒，内部信号量最多允许 4 个请求同时处理。三次都请求相同的 16 道模拟题；未指定 `--out`，所以每次都会重新请求。

| 客户端最大并发 | 成功/失败 | 用时 | 吞吐 |
| ---: | ---: | ---: | ---: |
| 1 | 16/0 | 16.24 秒 | 0.98 题/秒 |
| 4 | 16/0 | 4.15 秒 | 3.86 题/秒 |
| 16 | 16/0 | 4.12 秒 | 3.88 题/秒 |

从并发 1 到 4，吞吐约变为 **3.94 倍**；从 4 到 16 只多约 **0.02 题/秒**。原因是模拟服务一次最多处理 4 个请求，多余请求只能排队。这说明**提高客户端并发上限不等于提高服务端处理能力**。这里只跑了每档一次、每次 16 题，数字用于教学，不作为真实服务的容量结论。

最初的 4 题对比也符合这一点：并发 1 用时 4.12 秒、0.97 题/秒；并发 4 用时 1.10 秒、3.63 题/秒。

### 重试、续跑与失败恢复

1. `--demo-fail-once` 使第 2 题首次返回 HTTP 503。脚本等待 0.25 秒后重试，最终 4 题全部成功。
2. 首次保存 4 题到 `runs/day18_resume_demo.jsonl`；第二次运行同样的 4 题时，显示“已有 4、待跑 0”。把目标扩到 8 题时，显示“已有 4、待跑 4”，只请求第 5～8 题；成功文件最后有 8 行。
3. `--demo-fail-always` 使第 2 题持续返回 HTTP 503。重试两次后，本次成功 3 题、失败 1 题，退出码 1；成功文件 3 行，失败文件 1 行。
4. 去掉故障开关、沿用同一成功文件再次运行，只补跑第 2 题；退出码 0，成功文件共有 4 行。历史失败文件仍有 1 行。

这里的“断点续跑”通过先保存 4 题、再扩大到 8 题演示。真实中断后使用**同一批题目和同一结果路径**重新启动，读取 ID 并跳过已完成题的逻辑相同。

## 为什么用 `asyncio`

请求模型 API 时，客户端多数时间在**等待网络和服务端返回**，属于 I/O 密集工作。`await` 使等待中的请求让出执行机会，同一个事件循环可以管理许多请求。线程同样能处理 I/O；GIL 并不意味着网络请求不能用线程。这里选协程，是因为大量等待任务的调度较轻，且容易用信号量限定并发。

本地模型的计算是另一回事。`asyncio` 不会让单题的 GPU 推理自动变快；CPU 密集的数据处理可考虑多进程或原生库，GPU 服务的吞吐还取决于批处理、显存和服务端调度。

## 当前边界与接真实服务

上述并发与故障恢复实测使用脚本默认生成的“第 1 道题”等模拟文本，服务端只回显文字。它验证了**请求调度、容错、落盘和恢复**，没有测量 Qwen 的能力。随后接入 DeepSeek API，并完成本笔记末尾的 MMLU 50 题小实验。模拟服务的吞吐数字不能当作真实服务的容量结论；真实服务的并发上限和吞吐仍需单独测量。若输出路径已存在，应保持题目、提示词和评分设置一致，或换新路径。

例如，题目文件的两行可以是：

```jsonl
{"id": 101, "question": "1+1 等于几？", "gold": "2"}
{"id": 102, "question": "水的化学式是什么？", "gold": "H2O"}
```

把它保存为 UTF-8 JSONL 后，可用 `--input`、`--url`、`--model`、`--out` 指定真实服务和结果路径。若服务需要密钥，先在环境中设置密钥，再传 `--api-key-env`。**不要把模拟服务回显结果的准确率当作模型分数。**

```powershell
python .\src\async_eval.py --input '.\data\questions.jsonl' --model '服务中的模型名' --url 'http://127.0.0.1:8000/v1/chat/completions' --concurrency 4 --out '.\runs\api_eval.jsonl'
```

面试时可以概括为：**长时间评测中途崩溃，逐题落盘并按稳定 ID 续跑；单题故障隔离记录；对可恢复错误做有限退避重试；用并发测试找到服务端瓶颈。**要明确本次吞吐来自模拟服务，不能描述为 Qwen 实测。

## 2026-10-09 补充：接 DeepSeek API 做单题连通测试

DeepSeek 提供 OpenAI 兼容的 Chat Completions 接口，可直接作为本脚本的远程服务端。本地无需运行 `day18_mock_api.py`，但需要 DeepSeek API Key、可用额度和网络连接。按当日[官方入门文档](https://api-docs.deepseek.com/guides/codex)与[模型页面](https://api-docs.deepseek.com/quick_start/pricing/)，测试使用 `https://api.deepseek.com/chat/completions` 和 `deepseek-flash`。API 按 token 计费，首次只发一题。

单题输入文件 `data/day18_deepseek_smoke.jsonl` 是本地生成的原始数据，不入库。客户端支持 `--thinking disabled --max-tokens 16 --temperature 0`；这些参数用于控制单题测试的输出，参见[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)。不要把 API Key 粘贴到聊天或写进仓库；在 PowerShell 中用隐藏输入设置当前会话的 `DEEPSEEK_API_KEY`，再用 `--api-key-env DEEPSEEK_API_KEY` 让脚本读取。

这条单题测试只验证真实 API 的连通和结果记录。`exact_match` 对模型原文与 `gold` 做严格字符串比较；单题成绩不能代表模型在正式 benchmark 上的能力，也不能和本项目的 Qwen 分数直接比较。
